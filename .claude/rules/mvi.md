# MVI / presentation rules

Each screen: `UiState` (sealed: Loading/Success/Error), `UiAction` (one-shot via `Channel(BUFFERED)`, `receiveAsFlow()`), `Event` (user intents), `ViewModel`. Full detail: `docs/CONVENTIONS.md`.

- `uiState` derived via `combine(InternalState, domainFlows)` — no manual `collect` in `init`. **Exception 1:** a screen with no UI-only state (no filter, no selection — e.g. a flat manage-list screen) may derive `uiState` directly from the domain flow (`.map`/`.catch`/`.stateIn`), skipping `combine`/`InternalState` entirely rather than declaring an empty placeholder state. Confirmed for `SectionsViewModel`/`TagsViewModel` (#41/#43), `AllPrioritiesViewModel` (#28) and `ArchivedItemsViewModel` (#168). **Exception 2:** a form whose fields always render (no real screen-level load) doesn't need `Loading`/`Error` in `UiState` at all — just a plain `data class` mutated directly by `onEvent`/a one-shot `init` load; a background-data failure degrades silently (empty list, not a screen error), a real failure (e.g. editing a missing item) is a one-shot `ShowSnackbar` + `NavigateBack`, not a blocking state. Confirmed for `ItemFormViewModel`. **Exception 3:** a screen whose state pieces have genuinely different write-sources — UI-only state mutated directly by user events, query-derived data with no load/error of its own, and screen-readiness (Loading/Success/Error) — may expose them as independent `StateFlow`s instead of one `combine`d `UiState`, each collected separately by the Screen. Not a general escape hatch for "this got complex": only when the pieces really are driven by different producers (event vs. query vs. readiness), not just grouped by feature area. Confirmed for `HomeViewModel` (#102) — `filterState` (event-driven), `itemsState` (query-derived, no Loading/Error), `uiState` (readiness-only, scoped to `hasAnyItem`); also `SettingsViewModel` (#183) — `dialogState` (event-driven, pre-existing) and `accountUiState` (resolved once from `GoogleAuthUseCase.getSignedInAccount()`, not query-derived) sit alongside `uiState`, since a Google-account identity check isn't the same producer as the screen's own dialog/readiness state.
- Use case facades (`SectionUseCase`, `TagUseCase`, `ItemDetailUseCase`, `ItemFormUseCase`, `HomeUseCase`, `GoogleAuthUseCase`, `BackupUseCase`) compose existing single-purpose use cases to cut a ViewModel's constructor param count — one method per operation, each just delegating, never touching a repository directly. Name by entity when one screen uses the full CRUD set (Section/Tag); name by screen when the entity spans several screens with different operation subsets (Item). A single generic facade covering everything was tried and rejected (no clear owner, hard to find where a method is actually used). When a facade grows past the `LongParameterList` threshold, split by context instead of suppressing the lint — `BackupUseCase` (#16) split into `GoogleAuthUseCase` (sign-in/session) + a leaner `BackupUseCase` (operations taking an account, building the `Drive` service internally), mirroring the existing `GoogleAuthRepository`/`BackupRepository` boundary.
- `combine` is pure — never `_action.send(...)` or suspend inside it. Side effects go in `onEvent` handlers / `LaunchedEffect` in the Screen.
- No manual joins in the ViewModel — data arrives ready from the use case.
- No `.value = ...` (use `.update { ... }`); no `(uiState.value as? Success)` cast; no `Context`/`AndroidViewModel` (encapsulate in a repository).
- **State transitions that touch more than one field, or carry any conditional logic, live on the `UiState` class itself as a public named function** (`fun toggleReminder(enabled: Boolean): AddItemUiState`, `fun setTag(tagId: Long): AddItemUiState`, ...), called from `onEvent` as `_uiState.update { it.functionName(...) }`. The ViewModel should not need to know *how* one field's change cascades into others — that composition belongs next to the fields it touches, in the state class, not scattered across `onEvent` branches. Reserve inline `.update { it.copy(field = value) }` for genuinely single-field, no-side-effect changes. Confirmed the hard way (#130, 2026-08-09): `OnReminderToggled` was first written as a multi-field inline `.copy()` in the ViewModel, then — still wrong — as a *private extension function in the ViewModel file* mirroring an existing bad example (`toggleTag`); both got corrected to a public `toggleReminder(enabled: Boolean)` method living on `AddItemUiState`/`ItemDetailUiState` themselves.
- No hardcoded UI strings — `@StringRes` for snackbars, `e.message.orEmpty()` for errors.
- `:feature:*` depends only on `:domain` + `:uds`, never `:data`. **Exception:** `:core:backup` does depend on `:data` — it manipulates the Room database file directly (close/checkpoint/path) for backup/restore, not just via a repository interface.
- Reuse `:uds` components (TopBar/Loading/Error/Empty/ListItem/dialogs, most under `uds/components/legacy/` for now) — don't reimplement inline. Red/amber only for due-date urgency.
- **`:feature:*` never reads `LocalUdsExtendedColors` (or any other `:uds` `CompositionLocal`) directly.** It's an implementation detail of how `:uds` components color themselves internally, not a public API for feature code to reach into — pulling a color out of it to hand-roll a `Text`/`Icon` tint inline is exactly the "don't reimplement inline" violation above, just via a theme token instead of a whole component. Need a color that isn't already a plain `MaterialTheme.colorScheme.*` role? Either use an existing `:uds` component that already carries that color (e.g. `DueBadge`, `PriorityRow`) or add a new small `:uds` component/param instead of importing the `CompositionLocal` into feature code. **Known pre-existing debt, not yet migrated** (predates this rule — don't touch as a drive-by, it's its own cleanup): `feature/items/.../DueDateRow.kt`, `feature/items/.../fields/CompletionField.kt`, `feature/items/.../fields/DueDateField.kt`, `feature/home/.../DueBadgeMapping.kt`.
- **Any `ModalBottomSheet`/`Dialog`/`Popup` composable splits into two functions: an outer one that owns `ModalBottomSheet`/`rememberModalBottomSheetState`, and an inner `*Content` (or `*SheetContent`) with the actual UI, taking no sheet-specific params.** The `@Preview` always calls the inner `*Content` function directly, never the outer one. Reason: `ModalBottomSheet`/`Dialog`/`Popup` open in a separate platform window, and Android Studio's static `@Preview` renderer does not composite that window's content into the preview image — the outer function **always renders empty in a static preview**, regardless of any state passed to it (confirmed: adding a hoisted `visible: Boolean` param to try to preview "shown vs. hidden" changes nothing, since the emptiness is a window-compositing limitation, not a state problem). This is not project-specific style, it's the only way to get a working preview at all, and it is easy to default back to plain Material Design guidance (which does not surface this gap) when building a new sheet from scratch. Confirmed pattern across every sheet in the codebase: `AddItemSheet`/`AddItemSheetContent`, `ItemHistoryBottomSheet`/`ItemHistorySheetContent`, `SeedScopeBottomSheet`/`SeedScopeSheetContent`, `SelectionBottomSheet`/`SelectionSheetContent` (`:uds`, #130) — the `*Content` function is `public`/no modifier (not `private`) specifically so a different module's own sheet (e.g. `RecurrenceBottomSheet` in `:feature:items` wrapping the generic `SelectionBottomSheet`) can preview it directly too.
- **A field that opens one `ModalBottomSheet` for its own value lives in a single file** (field + sheet + one `@PreviewLightDark` together, ~100-130 lines is fine, don't split just to keep files small). **A field that needs more than one sheet (a list sheet plus a sub-selection sheet, e.g. `RecurrenceField` → `RecurrenceBottomSheet` → `EveryNDaysBottomSheet` for #130's "every N days" stepper) gets its own subpackage under `fields/` instead** (`fields/recurrence/`), one file per composable (`RecurrenceField.kt`, `RecurrenceBottomSheet.kt`, `EveryNDaysBottomSheet.kt`), each with **its own** focused preview — don't force one giant provider to span multiple sheets' files just because the single-sheet case does. Within each file, still cover that file's own states in one `@PreviewLightDark` driven by one `PreviewParameterProvider`, using a private `sealed interface` of scenarios (e.g. a field's `EmptyField`/`FilledField`) that the preview function `when`s over — one provider per file, not a preview function per scenario. Helpers shared across the package's files (e.g. `recurrenceOptions()`, the `Recurrence.label()` extension) are `internal`, not `private` — top-level `private` in Kotlin is file-scoped, so it won't compile from a sibling file even in the same package.
- **A screen with a "Save" affordance can auto-save per action instead of batching everything behind one explicit button.** Confirmed for `ItemDetailViewModel` (#133): every structured `FieldEvent` (a picker/toggle/selection — anything except free-text fields) saves immediately through one shared `persist()`; free-text fields (title/description) debounce (~500ms, `Job` cancelled and relaunched per keystroke) instead of saving on every character; any structured field firing while a text debounce is pending cancels it first (the immediate save already captures the latest text from `_uiState.value`, so the stale debounce would just redo the same write). Auto-save stays silent on invalid state (e.g. blank title just skips the write, no error shown) — only the explicit "Save" button surfaces that validation, since interrupting the user mid-edit for a field they haven't gotten to yet is worse than a quiet no-op. A pending debounce still owed when the screen closes is flushed synchronously in `onCleared()` (`runBlocking`, since `viewModelScope` is already torn down by the time `onCleared()` runs — see `docs/CONVENTIONS.md`'s Testes section for why `Job.isActive` can't detect this and a plain flag is used instead).
- ViewModels are tested (MockK + Turbine) and gated by `koverVerify` since #41 — each `:feature:*` with a tested ViewModel needs the `kover` plugin applied and added to `app/build.gradle.kts`'s aggregation. Composables/Screens stay excluded (no required tests for them yet).
- ViewModel tests: mock fields via `@MockK` + `MockKAnnotations.init(this)` (not inline `= mockk()`). Test names: `` `when <condition/event> should <expected behavior>` `` (no comma, no "given") — since #43.
- Screen: `koinViewModel()` + `collectAsStateWithLifecycle()`; resolve `@StringRes` via `LocalResources.current`; wrap nav callbacks in `rememberUpdatedState`.
- **A cohesive subset of an `Event` sealed interface (events that share a handler, a mode, or a lifecycle) can be grouped under a nested marker `sealed interface` implementing the outer `Event`** (`sealed interface SelectionEvent : HomeEvent`), with its member events declared flat alongside the rest — not nested inside the marker's own body — so every event keeps the same one-level qualified name (`HomeEvent.OnItemLongPressed`, not `HomeEvent.SelectionEvent.OnItemLongPressed`). The ViewModel's outer `when` gets one branch for the whole group (`is HomeEvent.SelectionEvent -> handleSelectionEvent(event)`) that narrows into its own exhaustive `when`. `//region`/`//endregion` around each group keeps a growing `Event` file scannable. Confirmed for `ItemDetailEvent.FieldEvent` (#133, field-mutation events sharing the auto-save handler) and `HomeEvent.SelectionEvent` (#140, the 4 selection-mode events sharing `handleSelectionEvent`).
- **When a `@PreviewLightDark` needs to exercise a state that cuts across an existing `PreviewParameterProvider`'s fixtures (e.g. a selection mode applicable to any of them), wrap the existing base type in a one-line `data class XPreviewScenario(val <base>: <BaseType>, val extraField: T = default)` instead of writing a second, parallel provider or duplicating fixtures.** The provider's `values` becomes the existing base fixtures mapped through the wrapper (unchanged, `extraField` at its default) plus one appended scenario with `extraField` set — `baseFixtures.map { XPreviewScenario(it) }.plus(XPreviewScenario(base = ..., extraField = ...)).asSequence()`. Name the wrapped field after the base type it holds (`itemsState: HomeItemsState`, `fixture: HomePreviewFixture`) — it varies by what's being wrapped, that's expected, not an inconsistency to fix. Confirmed for `ItemsListPreviewScenario`/`ItemsGridPreviewScenario`/`ItemsContentPreviewScenario` (#140) — all three needed a `selectedItemIds` scenario on top of `HomePreviewProvider`'s existing fixtures.
